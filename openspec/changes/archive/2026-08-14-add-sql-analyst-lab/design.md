# Add SQL Analyst Lab — Design

## Overview

The change adds a new learning module `learning/02-sql-learning/sql-analyst-lab/` ("Data-to-Insight Case Studies") as the level beyond `sql-skill-push`. Each of the 3 cases (Brew & Co., MarketHub, NovaTel) presents ONE open-ended main business question and walks the learner through the 4-step framework from `learning/04-data-to-insight/data-to-insight.md`: (1) fix ~3 Northstar metrics + ~3 dimensions before touching data, (2) break the ambiguous question into sub-questions across the 4 buckets (Overall Trends, Growth Rates, Performance Measurement, KPI Reporting), (3) write one SQL query per sub-question (metric sliced by dimension), (4) surface strong insights + recommendations (weak-vs-strong standard), with the Running Log as a working habit. Model queries are authored and executed against the reused sql-skill-push SQLite datasets via `_tools/run_query.py`; expected results are captured from real execution. A new `analyst` learning-progress track (3 Case units) is registered registry-data-only.

## Design Decisions

### Decision 1: Sibling module, not a level-4 of sql-skill-push

**Choice**: Create `learning/02-sql-learning/sql-analyst-lab/` as a new module folder alongside `sql-skill-push/` rather than adding `04-advanced` challenges or extending the existing level folders.
**Rationale**: sql-skill-push is deliberately exact-match challenge practice; the analyst lab is open-ended, question-driven analysis with a different pedagogical contract (rubric + insight writing, not exact-match only). Mixing them would blur both contracts, and sql-skill-push must remain byte-identical per the reuse discipline.

### Decision 2: Reuse datasets by relative path, never copy

**Choice**: All model queries in the lab reference the sql-skill-push `.db` files via relative paths from the repo root (e.g. `../../sql-skill-push/datasets/01-beginner/retail.db`). No dataset files are copied, regenerated, or modified.
**Rationale**: The datasets are deterministic and already verified; copying would duplicate ~3 MB of binaries, risk drift between copies, and violate the reuse discipline. Relative paths work with `run_query.py` from anywhere in the repo.

### Decision 3: 3 cases with decreasing scaffolding

**Choice**: Case 01 (Brew & Co., retail) has the highest scaffolding — metrics, dimensions, and full bucket-to-sub-question mapping are suggested. Case 02 (MarketHub, ecommerce) has medium scaffolding — metrics/dimensions suggested but bucket mapping partially open. Case 03 (NovaTel, telecom) has minimal scaffolding — learners derive metrics/dimensions themselves.
**Rationale**: Scaffolding fade is a proven teaching pattern: early cases model the framework explicitly; later cases force the learner to apply it independently.

### Decision 4: Case anatomy = case.md + expected/ + work/

**Choice**: Each case folder contains `case.md` (brief, dataset pointer, limitation notes), `expected/` with `01-scope.md`, `02-questions.md`, `03-queries.sql`, `03-results.md`, `04-insight.md`, and `work/` (learner scratch, `.gitkeep`).
**Rationale**: Mirrors the sql-skill-push `challenges.md` + `solutions/` convention (expected results visible to the learner for self-check) while adding the scope/question/insight artifacts the 4-step framework requires. The `work/` dir gives learners a place to draft before comparing.

### Decision 5: Verification = SQL exact-match via run_query.py + text rubric

**Choice**: `03-results.md` is generated by executing `03-queries.sql` with the existing `python learning/02-sql-learning/sql-skill-push/_tools/run_query.py <db> <sql-file>` helper (markdown-preview output + row count). Insight quality is checked against the weak-vs-strong standard from the pedagogy source (strong = trend + fluctuation + anomaly + root cause + recommendation).
**Rationale**: Reuses the module's verified helper (no new tooling), gives learners an exact output to reproduce, and keeps insight grading qualitative where exact-match is meaningless.

### Decision 6: Track registration is registry-data-only

**Choice**: Add the `analyst` row to `learning/00-notes/tracks.md` (id, name, roadmap = module README, notes dir = `learning/00-notes/05-analyst-lab/`, 3 Case units) and create the notes dir with README. No `learning-progress` skill/blueprint/manifest/spec edits and no ADR.
**Rationale**: The registry is explicitly the single source of truth for tracks — appending a row is the documented way to add a track without touching the skill. The existing `04-sql-push/README.md` notes-dir convention is followed for `05-analyst-lab/`.

### Decision 7: No query-inspector contract change

**Choice**: The lab's README documents an optional usage note — the learner may copy `work/` queries to `script/01-sql/` and run `@query-inspector` for review — but neither the agent, its spec, nor its contracts are modified.
**Rationale**: query-inspector already accepts learner-submitted SQL in `script/01-sql/`; the lab only needs to point at that existing capability. Changing its contract is out of scope.

## Edge Cases

- **Telecom has no YoY**: billing spans only `2025-12-01` and `2026-01-01`, so only MoM is possible. Case 03 `case.md` states this limitation explicitly, and no model query attempts YoY — the framework's dataset-limitation discipline is enforced, never fabricated comparisons.
- **Repeat purchase rate is ambiguous**: "repeat" can mean ≥2 orders, ≥2 orders in a window, or distinct-customers-with-2+-orders ratio. Case 02 fixes the definition in `01-scope.md` (customers with ≥2 completed orders ÷ customers with ≥1 completed order over the full order history) and every model query implements that exact definition consistently.
- **work/ must exist in git**: each `work/` folder ships a `.gitkeep` so the empty scratch space is preserved.
- **Relative path resolution**: all dataset references and helper paths are relative to the repo root so `run_query.py` invocations work regardless of the caller's working directory.
- **Reuse discipline**: no writes ever target `learning/02-sql-learning/sql-skill-push/`; verification asserts the subtree shows no git changes.
